A program opens a strange file. A button produces a surprising result. An old tool does something your new one cannot. How do you work out what happened when you do not have the original source code?

You collect evidence, form a small hypothesis, and test it. Then you turn what you learned into a specification someone else could implement.

Start with one feature.

“Read this file” is a useful first project. “Rebuild Photoshop” is thousands of projects hiding inside one sentence.

First, untangle the viral claims.

REA - Reverse Engineer Anything is the GitHub project behind this guide. Its page showed roughly 284,000 stars when checked on 16 October. That is a popularity snapshot, not a measure of how well it handles your app.

REA connects coding agents to analysis tools. It can put disassembly, pseudocode and other findings into the agent's workflow. For native programs, it works with backends such as Ghidra, Hopper or IDA. Think of it as a bridge between the investigator and their instruments, rather than a button that restores every program's source.

And the person rebuilding Adobe-style apps?

That is a related story: Brandon Thomas and the ArtCraft family of applications. PhotoCraft's maintainers describe it as a Rust implementation built from public specifications and observed behavior, without Adobe's proprietary code or assets.

They also explicitly call it early alpha and say it is not yet a daily professional replacement for Photoshop. A familiar toolbar and a working export are meaningful progress. They do not establish parity across decades of features, file compatibility, color handling and plugins.

There is no source here establishing that ArtCraft used REA. Understanding behavior, rebuilding it independently, and recovering original source are three different things.

The process that actually works

  1. 1. Observe
  2. 2. Compare
  3. 3. Explain
  4. 4. Rebuild
  5. 5. Test

1. Ask a question you can answer.

Choose an outcome: “How is the export's width stored?” or “What happens when the search field is empty?” Record the target version, operating system, settings and your starting file. Keep an untouched copy. A future update may change the answer.

2. Change one thing.

Save the same document twice, changing only its title. Export the same image at two widths. Send an empty search, then one word, then an unusual character. Differences are useful when you know which input caused them.

3. Separate observations from guesses.

“Byte 8 changed from 10 to 11” is an observation. “This stores the score” is a hypothesis. Keep both in a small evidence log. If an AI says a function validates a file, ask for the branch, string, input or experiment supporting that claim.

4. Predict a result you have not checked.

If two bytes represent a little-endian number, predict what 256 will look like. If a field is a length, predict what happens after adding an item. A theory that explains old examples can still be wrong; an unseen test is where it starts earning trust.

5. Rebuild the smallest useful behavior.

Write a specification with inputs, outputs, errors and edge cases. Implement from that specification. Compare both implementations on the same fixtures. Add malformed files, empty values and boundary cases before broadening the scope.

The question to keep asking:

“What observation would prove this explanation wrong?” It is a better next step than asking the model whether it is confident.

Ghidra and JADX are open source. REA's code is MIT licensed; connected tools and model services can have separate licenses or costs. You do not need a paid disassembler for the lab.

Route A: follow a web app's request.

Use your own site, a local example or a target you have permission to inspect. Choose one interaction, such as submitting a search.

  1. Open Chrome DevTools and its Network panel. Clear the request list. Turn on Preserve log if the action navigates away.
  2. Perform the action once. Filter to Fetch/XHR and find the relevant request by its timing and content.
  3. Record its method, path, query parameters or payload, response status and response shape. Keep credentials out of your notes.
  4. Repeat with a single changed input. Does the browser send the filter, or filter an already downloaded list?
  5. Write the behavior as a contract. Example: “Empty input returns an empty list; three matching records render in this order.” Implement a local mock and compare its visible result.

The official Network guide explains the panel and request details. A response shows what the server returned, not its private implementation. You cannot recover a remote recommendation algorithm simply by downloading the page. HAR exports can contain secrets; do not publish an unreviewed capture.

Route B: start with a string in a desktop app.

For a compiled program, use a copy of an executable you own or are authorized to analyze. Do not run an unfamiliar executable just to find out what it does.

  1. Get Ghidra from its official releases. Follow the version's Getting Started requirements; the current document specifies a 64-bit Java 25 JDK.
  2. Create a non-shared project, import the copied program, and allow automatic analysis. Check that the selected architecture matches the file.
  3. In CodeBrowser, open Window → Defined Strings. Search for a distinctive message from the feature, such as an export error.
  4. Follow references to that string. Inspect the surrounding function and its callers in the decompiler and listing. Note the checks leading to the message.
  5. Give functions provisional names such as maybe_read_header. Record addresses and evidence. Decompiled pseudocode is an approximation, not the author's original source.
  6. Test the proposed rule against controlled examples in your own program. If it predicts the wrong result, revise the explanation before copying its logic into a replacement.

Optimizations, missing symbols, indirect calls and unusual formats can make this difficult. An agent's plausible function name does not resolve those gaps.

Android is a different starting point.

Open your own APK in jadx-gui. Start with the manifest, locate the relevant screen or distinctive text, and follow usages into event handlers. JADX reconstructs Java-like source from Android bytecode, with limitations. Native .so code needs a native tool. Record missing or failed decompilation instead of treating the view as a complete source tree.

Try it: decode a tiny mystery file.

No installation beyond Python 3. No account. No unknown executable. Download the ZIP, extract it, and open a terminal inside its lab folder.

We created this format and its fixtures for teaching. This is a reproducible exercise, not a claim that we blindly decoded a real product or tested REA.

Step 1: compare three controlled saves.

File A was saved with values 10 and 20. B changes only 20 to 21. C adds a third value, 30. If xxd is installed, inspect them with:

xxd -g 1 samples/a.lbx
xxd -g 1 samples/b.lbx
xxd -g 1 samples/c.lbx

Or explore the same bytes here. Colors show the proposed fields; selecting another sample shows what changes.

Blue: signatureLime: countPink: values

Step 2: write a theory.

The first four bytes stay fixed: 4c 42 58 31, or ASCII LBX1. They look like a format signature. The next four start with 02 for A and B, then 03 for C. Perhaps they store the item count.

The remaining values appear in pairs: 0a 00 means 10, 14 00 means 20, and 1e 00 means 30. Our working theory is a four-byte little-endian count followed by two-byte little-endian unsigned values. Three small examples do not yet establish every possible rule.

Step 3: predict an unseen save.

The held-out fixture is 4c 42 58 31 03 00 00 00 00 01 01 02 ff ff. Under this theory, 00 01 is 256, 01 02 is 513 and ff ff is 65535. Now check:

python3 inspect_lbx.py samples/held-out.lbx
# Expected: [256, 513, 65535]

python3 inspect_lbx.py samples/truncated.lbx
# Expected error: size does not match count

Step 4: build a reader that rejects bad input.

Python's struct module lets us state the byte order and number sizes explicitly. The core reader is short:

def parse(data):
    if len(data) < 8:
        raise ValueError("truncated header")
    if data[:4] != b"LBX1":
        raise ValueError("wrong signature")
    count = struct.unpack_from("<I", data, 4)[0]
    if len(data) != 8 + count * 2:
        raise ValueError("size does not match count")
    return [struct.unpack_from("<H", data, 8 + i * 2)[0]
            for i in range(count)]

< selects little-endian byte order; I reads an unsigned four-byte integer and H reads two bytes. The complete downloadable script includes imports and a command-line entry point.

What we actually checked: all four valid fixtures decoded correctly. Five malformed cases were rejected: a truncated record, a short header, a wrong signature, extra trailing data and an impossible count. Nine checks passed locally on 16 October. This only verifies our teaching format and parser.

With a real format, your next questions might be compression, checksums, optional fields and versions. Make a new controlled file for each question rather than inventing the answer.

Where REA fits into this

Once you understand the process, REA can help a coding agent operate the analysis tools and follow evidence across them. It does not remove the need for a narrow question or tests.

1. Review the setup before running it.

Use a project you control. Read the official installation instructions. They currently support Node 22.19+ within 22.x, 24.11+ within 24.x, or 26+. Check your version first:

node --version
npx rea-agents@latest setup

Choose the intended coding agent, review the proposed paths and changes, and approve only what you need. Setup adds an MCP connection and workflow instructions; restart the named agent afterwards. Native analysis needs a compatible backend. JavaScript analysis does not require a native disassembler.

2. Choose a small, explicit target.

For example, the documented JavaScript command can be run through the package runner:

npx -y rea-agents@latest analyze-javascript-application /absolute/path/to/your-app --json

The -y flag accepts npm's package-runner prompt. Read the package and installation information first; this downloads and executes a tool. We have not installed or benchmarked REA for this article.

3. Keep the evidence trail.

Ask the agent for the exact source location, address or observation behind each conclusion. Save the target version, tool versions, commands, fixtures and unresolved questions with your notes. Analysis runs locally, but findings passed to a model enter its context; your model provider's data handling still matters. Do not assume “local tool” means “no data leaves the machine.”

Give the agent a case, not a wish.

A good starting prompt defines the feature, the available evidence and what success means. Copy this and replace the bracketed fields:

Target: [an app/file I own or am authorized to analyze]
Question: [one specific behavior]
Version and environment: [exact build, OS, settings]
Evidence: [paths to controlled input/output examples]

First propose a small investigation plan.
Separate observed facts, hypotheses and unknowns.
For each conclusion, cite a file/line, function/address,
or reproducible input/output observation.
Propose a test that could disprove each main hypothesis.
Do not execute unknown binaries or change the original.
Do not install tools or upload data without asking.
Deliver a behavior specification and a test matrix.
Do not claim original source recovery from pseudocode.

Hand a specification to the builder.

If you want an independent implementation, separate investigation notes from the build instructions. A stricter clean-room process needs real access separation; starting a second chat while both agents can read the same files does not establish it.

Implement only the attached behavior specification.
Use original code and assets. Do not fetch the target.
List assumptions before implementing missing behavior.
Run every supplied input/output fixture.
Add boundary, empty and malformed-input tests.
Report passed tests, failures and unsupported cases.
Keep implementation claims limited to those results.

Before calling it done

  • Can the result handle an input you did not use while designing it?
  • Does it preserve the details the user needs, such as precision, order or export compatibility?
  • Does it fail clearly on unsupported versions and damaged inputs?
  • Could another person reproduce your findings from the saved evidence?
  • Have you distinguished a promising prototype from a dependable replacement?

Use owned, open-licensed or explicitly authorized targets. Keep proprietary code, artwork and credentials out of a new implementation. This guide does not cover bypassing licensing, authentication or paid access. Permission to inspect and permission to redistribute are separate questions.

The useful result is not “the AI understood the app.” It is a small explanation that predicts the next experiment, followed by an implementation that passes it.
